# Отчет по итогам тестирования (Fuzzing & Load Testing)

## 0. Юнит-тестирование (Unit Testing)
Перед проведением сложных видов тестирования была выполнена проверка базовой логики приложения с помощью стандартных JUnit-тестов.
*   **Результаты**: Все 23 теста пройдены успешно, ошибок не обнаружено.
*   **Покрытие (Coverage)**:
    *   **Lines**: 99%
    *   **Branches**: 95% (за исключением логики обработки невалидных `action`, что и стало фокусом дальнейшего фаззинг-тестирования).

Высокое покрытие тестами не гарантировало отсутствие дефектов при нестандартных входных данных, что подтвердили результаты фаззинга.

## 1. Фаззинг-тестирование (Fuzzing)
Инструменты: **JUnit 5**, **jqwik**, **Jazzer**.

### Выявленные дефекты:
В ходе фаззинга были обнаружены критические ошибки обработки входных данных в эндпоинте `/endpoint`. Приложение возвращает **500 Internal Server Error** вместо ожидаемых 400 (Bad Request) или 401 (Unauthorized) в следующих сценариях:

| Входной параметр | Значение (Payload) | Ожидаемый результат | Фактический результат |
| :--- | :--- | :--- | :--- |
| `action` | Пустая строка (`""`) | 400 Bad Request | **500 Internal Server Error** |
| `action` | Строка `"null"` | 400 Bad Request | **500 Internal Server Error** |
| `action` | случайная строка ASCII | 400 Bad Request | **500 Internal Server Error** |
| `token` | Некорректный формат (Ascii/Garbage) | 400 Bad Request | **500 Internal Server Error** |

**Рекомендация:** Реализовать строгую валидацию входных параметров и добавить глобальный обработчик исключений (`@ControllerAdvice`), чтобы предотвратить падение контекста в 500 ошибку при некорректных запросах.

## 2. Нагрузочное тестирование (Load Testing)
Инструмент: **Gatling**.

### Сценарий 1: RPS = 500 (Умеренная нагрузка)
*   **Успешность (Success Rate):** ~80% OK / 20% KO.
*   **Проблемы:**
    *   **403 Forbidden (~56-72% ошибок):** Указывает на проблемы с управлением токенами или блокировками (LockingAspect) при параллельном доступе.
    *   **Timeouts (~27-42% ошибок):** Среднее время ответа растет, достигая лимита в 60с.
*   **Состояние JVM:** Наблюдается высокая загрузка Old Gen и частые циклы очистки (GC), что приводит к "stop-the-world" паузам. См. [gc-monitor.txt](file:///c:/WSL/Java/AQA_NC/gc-monitor.txt).

### Сценарий 2: RPS = 1000 (Критическая нагрузка)
*   **Успешность (Success Rate):** ~60% OK / 40% KO.
*   **Критическая проблема: Исчерпание портов (Port Exhaustion)**
    *   Ошибка: `ConnectException: Cannot assign requested address`.
    *   Диагностика (`ss -s`): Обнаружено ~108 000 TCP соединений, из которых более 35 000 в статусе `closed`/`timewait`. См. [Данные rps 1000.txt](file:///c:/WSL/Java/AQA_NC/Данные%20rps%201000.txt).
    *   **Причина:** Приложение или тестовый стенд не успевают освобождать сокеты при такой интенсивности запросов.
*   **Таймауты:** Более 36% запросов упали по таймауту 60с.

### Сценарий 3: Login Spike (Всплеск нагрузки)
*   **Условия:** 5000 одновременных попыток входа (`LOGIN`) на фоне фоновой нагрузки 1000 RPS.
*   **Результаты:** 100% OK (KO=0). Ошибок соединения или 403 в этом краткосрочном сценарии не зафиксировано.
*   **Проблема:** Значительная деградация времени ответа. 
    *   **Max response time:** ~11 секунд.
    *   **Mean response time:** 3.6 секунды.
    *   Более 56% запросов обрабатывались дольше 1.2с.
*   **Вывод:** Система выдерживает кратковременный всплеск без падений, но пользовательский опыт (UX) критически страдает из-за долгого ожидания.

---

## 3. Общие выводы и рекомендации
1.  **Стабильность**: Приложение не готово к нагрузке выше 500 RPS без тюнинга сетевого стека и изменения работы с памятью.
2.  **Архитектура**: Поставленный малый TTL на ConcurrentHashMap ведёт к GC проблемам. На мой взгляд, вместо этой структуры для токенов лучше использовать Postgres.
3.  **Сетевой стек**: Необходимо увеличить диапазон локальных портов (`ip_local_port_range`) и включить переиспользование сокетов (`tcp_tw_reuse`) на стороне сервера и тестового генератора.
4.  **Безопасность и Валидация**: Требуется немедленное исправление логики обработки ошибок (устранение 500-х ошибок при невалидном вводе).
